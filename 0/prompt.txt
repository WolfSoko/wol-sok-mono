  ## Findings, most severe first
  
  1. **Medium: a wish the host cannot read throws away the guest's ready as well** (`net/net-message.ts`, `case 'room'`)
     - What is wrong: the parser drops the whole `room` message when `wish` fails `isMatchLevel`.
     - Failure: a newer guest release adds an online level without bumping `BALANCE_VERSION`, so `NET_VERSION` is still equal. The guest wishes that level and says ready. The older host drops every `room` message from it, ready included, while the guest's own screen shows "ready".
     - This is the same forward-compatibility the PR relies on for features. The engine's own `pickMatchLevel` already treats an unknown level as "any level".
     - Fix: parse an unknown or invalid `wish` as `null` and keep `ready`. Reject the message only when `ready` is not a boolean. Add a parse spec for "unknown wish, ready true".
  
  2. **Low-medium: the host shows a stale "Ready" and wish for one round trip after its own pick or start** (`net/guest-room.ts`, `heard` is only ever set from `room` events)
     - What is wrong: the host emits no `setup` or `start` event to itself, so `heard` stays as it was until the guest's re-sent `room` message comes back.
     - Failure: the guest is ready for A. The host switches to B and for about one round trip sees "Ready" on the guest's card for B. The same happens with "{name} suggests X" right after picking X.
     - Race: the guest taps ready while the host's setup for B is still in flight. Its store still says A, so it sends `ready: true`, and the host shows ready for B until the guest receives the setup and retracts it. The wire carries no level, so the host cannot tell.
     - The spec says the host only mirrors, so this is tolerated, but it is visible.
     - Fix, either:
       - on the host, clear `heard.ready` (and a `wish` equal to the new level) on its own `setLevel` or `startMatch`; or
       - send the level that ready refers to (`readyFor`) over the wire, and have the host show ready only while it equals its current level.
  
  3. **Low: the host's `GuestRoom` subscribes late** (`net/guest-room.ts:69`)
     - What is wrong: the root service subscribes to `events$` in its constructor, and it is injected only by `OnlineRoomComponent`.
     - Failure: a `room` message that arrives before the host first renders the room is lost, because the guest re-sends only on change. That could happen with matchmaking's automatic first match, or a host whose screen is not the room yet.
     - Fix: instantiate `GuestRoom` eagerly where `OnlineSeatSync` and the other net services start, or keep the last heard state in `OnlineMatchService`.
  
  4. **Low (spec): the Ready button wording differs from the spec** (`menu/online-room.component.html` ~line 104-118)
     - Spec: `a toggle button "Ready", which turns into "Ready ✓" ("Not ready" to undo)`.
     - Code: the label is always "I'm ready" / "Ich bin bereit". Only the icon and `aria-pressed` change.
     - A fixed label with `aria-pressed` is the correct accessible toggle pattern, so this may be intended. Then the spec should be amended; otherwise the label should follow the spec.
     - The icon inside the button has no `aria-hidden="true"`, unlike the icons in the tags. A screen reader may read the ligature text "check_circle" or "radio_button_unchecked".
     - Fix: add `aria-hidden="true"` to that `mat-icon`.
