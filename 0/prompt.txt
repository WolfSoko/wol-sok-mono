  - **How Nx merges:** `node_modules/nx/dist/src/project-graph/utils/project-configuration-utils.js` (`mergeCreateNodesResults`, around lines 196-253) merges in this order: specified plugins (`@nx/oxlint` is one), then target defaults, then `project.json`/`package.json`.
  - **Spread support:** target defaults merge through the same `mergeCreateNodesResultsFromSinglePlugin` path. So a `'...'` spread there resolves against the inferred `@nx/oxlint` target, just as the local plugin's does.
  - **Matching:** `target-defaults.js` matches entries by target name or by executor. The schema (`nx-schema.json`, around lines 867-890) also offers `filter: { plugin, executor, projects }`.
  - **Replacement:** one entry does the plugin's whole job, with no code:
    `"targetDefaults": { "@nx/oxlint:lint": { "inputs": ["...", "{workspaceRoot}/package-lock.json"] } }`
    The alternative is `"lint": [{ "filter": { "plugin": "@nx/oxlint" }, "inputs": ["...", "{workspaceRoot}/package-lock.json"] }]`.
  - **Cost of the plugin:** about 180 lines of code and tests. It must stay right after `@nx/oxlint` in `nx.json` or the spread has nothing to keep. It also needs a `DEFAULT_TARGET_NAME` that must match `nx.json` by hand.
  - **The spec's reasons don't hold up** (decision 2, spec line 78). It rejected only `targetDefaults.lint`, saying that "the plugin keeps the rule in one tested module" and "a later change touches no nx.json".   - **What it does:** it walks up the folders from every `project.json` looking for a `tsconfig.json`, as a stand-in for "`@nx/oxlint` inferred a lint target here".
  - **Why that's the wrong layer:** `@nx/oxlint` decides that from its own oxlint config detection (`node_modules/@nx/oxlint/dist/src/plugins/plugin.js`).
