  **1. Does grouping by depth avoid the collision?** Yes.
  - Every handler invocation creates its own `tempfile.mkdtemp()` workdir with a fresh `contents/` folder, unpacks only that deployment's sources into it, and deletes it at the end (`shutil.rmtree`). The `Not a directory` error can only come from two sources inside one deployment.
  - Within one depth, no page can be the folder of another. Page A at depth d would have to be an ancestor of page B, and B's ancestors are all shallower than d. So each group's sources can never put a file and a folder on the same path.
  - Prune: `spa.construct.ts` sets `prune: false` on every deployment, so `s3 sync` runs without `--delete`. A later deployment never removes the keys of an earlier one.
  - retainOnDelete: it is not set. The handler then defaults it to `"true"`, so it never runs `s3 rm`, on Delete or on an Update that changes the destination.
  - destinationKeyPrefix: none, so every deployment writes to the bucket root.
  - Ordering: `addUpload` chains each deployment after `lastUpload` and makes `indexDeployment` depend on it. The order is build output (1), noCache override (3), depth-1 pages (4), depth-2 pages (5), then `index.html` (2) last. The depth-1 and depth-2 groups write disjoint keys (`blog` vs `blog/<slug>`), so their relative order does not matter.
