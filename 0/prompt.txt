  - Failure scenario: any `create` plan after the first deploy (see finding 2, a key deleted in the dashboard, or `--account-id` switching account). The old key is deleted, `refreshRelay` keeps the old token, Cloudflare answers 401 every 30 min, and `relay/turn` expires within an hour.   **2. bug: a failed secret read counts as "no secret", which rotates the live key.** `tools/relay/firebase-secrets.ts:43`, `provision.ts:53-61`.
  - `read()` returns null on any non-zero exit: network, quota, permission, a CLI hiccup. `storedUid` also returns null on unparsable JSON.
  - `planTurnKey` then plans `create` with `remove` set to every existing key, including the one in use.
  - Failure scenario: the second, "idempotent" run of `turn-key` hits a transient `functions:secrets:access` failure. It mints a new key and deletes the live one, which with finding 1 breaks the relay.
  - Fix: return null only for a real not-found (match the CLI's error) and throw on everything else. Never delete keys when the stored value could not be read.
  
  **3. bug (needs a check against Cloudflare): the field holding the new key's secret may be wrong.** `tools/relay/cloudflare-api.ts:102-107`, `provision.ts:83-86`.
  - `createTurnKey` is typed `{ uid, secret }` and writes `created.secret` without validating it.
  - As far as I remember, Cloudflare's "Create TURN key" answer names the bearer token `key` (`TURNCreateResponse.key` in the TS SDK), not `secret`. Context7 did not settle it. The spec also says `secret`, so it may have copied the same assumption.
  - Failure scenario: if the field is `key`, the stored secret is `{"id":"…"}`. `parseTurnKey` throws on every `refreshRelay` run. Every later `turn-key` run reports `keep`, because `storedUid` reads only `id`, so it never heals.
  - Fix: read `key ?? secret`, throw before writing when neither is a non-empty string, and have `storedUid` also require a `token`.
  
  **4. spec gap: the "survives expiry" check proves nothing, and its result is ignored.** `tools/relay/relay-check.ts:196-198, 300-307` and `turn-key.ts:310`.
  - The check holds the channel 120 s past a 60 s credential. Chrome refreshes TURN permissions only about every 4 min and the allocation at its lifetime minus 60 s (lifetime about 10 min). Neither refresh happens within 120 s, so `afterExpiry` comes out true even if the relay drops at the first refresh after expiry.
  - Cloudflare's docs say the `ttl` should exceed the longest expected session and suggest `setConfiguration()` to refresh, which hints that expiry does matter.

  - Fix: hold at least 11 min past expiry, make `afterExpiry` part of the exit code, or implement the `PeerLink` refresh (`setConfiguration` every `RELAY_REFRESH_MS`) regardless.
