# CLAUDE.md — wol-sok-mono

Angular + Nx monorepo. Read this before touching anything.

## Stack

- **Angular 22** — standalone components, zoneless change detection, Signals, `@if`/`@for`/`@switch` control flow
- **Nx 23** — monorepo orchestration, caching, affected commands
- **TypeScript 6.0** — strict mode
- **Build**: Vite (Analog/Vitest apps), Webpack + Module Federation (angular-examples)
- **Testing**: Jest (most unit tests), Vitest (Vite projects), Playwright (E2E)
- **Lint / Format**: oxlint (`.oxlintrc.json`, targets inferred by `@nx/oxlint`), angular-eslint for templates only (`eslint.config.mjs`, target `lint-templates`) and oxfmt (`.oxfmtrc.json`, driven by `nx format`)
- **UI**: Angular Material + CDK everywhere (no custom primitives if AM covers it)
- **State**: Angular Signals (local/sync), RxJS (async), NgRx Signal Store (bacteria game), Akita/Elf (older app-wide stores)
- **Backend**: Firebase (Hosting, Auth, DB), AWS CDK (S3/CloudFront infra)
- **Package manager**: npm (use `npm ci`, never yarn/pnpm)

## Engineering Principles (mandatory)

Long-term, strategic software engineering is required. A change that works but leaves the code harder to change is not done.

- **Improve the codebase with every feature and bug fix.** Leave the code you touch cleaner than you found it: extract duplication, split oversized files/functions/components, fix misleading names, remove dead code, and add missing tests around what you changed.
- **Fix root causes, not symptoms.** No workarounds or one-off special cases when the underlying design is the problem; fix the design.
- **Stay modular.** Small, focused units with one responsibility and narrow interfaces. Put logic in the right `libs/` layer (see Dependency Constraints) instead of growing app code; keep domain logic out of components and in testable services/stores/pure functions.
- **Clean Code is the standard.** Intention-revealing names, small functions, no magic values, no deep nesting, no copy-paste, single level of abstraction per function, explicit error handling.
- **Easy to maintain beats clever.** Prefer simple, readable code a newcomer can follow over terse or tricky solutions.
- **Scope of cleanup:** improvements to the code your change touches belong in the same PR. A larger refactor that the change exposes but doesn't need goes in its own PR (or an issue), so each PR stays reviewable.

## Coding Rules

1. **Standalone components only** — no NgModules
2. **Zoneless change detection** — never add `zone.js` imports or zone-dependent patterns
3. **Signals for state** — prefer `signal()`/`computed()`/`effect()` over manual subscriptions where possible
4. **OnPush everywhere** — `changeDetection: ChangeDetectionStrategy.OnPush`
5. **Angular Material** — use AM components consistently; don't roll custom UI that AM already covers
   - Exception (pacetrainer): the countdown ring (`pace-countdown-circle`) is a custom SVG, since `mat-progress-spinner` has no track ring
6. **Modern control flow** — `@if`, `@for`, `@switch` (not `*ngIf`, `*ngFor`, `*ngSwitch`)
7. **2-space indentation**, kebab-case filenames, `*.spec.ts` for tests
8. **Explicit `public`/`private`** in class members
9. **Strongly typed** — avoid `any`; use proper generics
10. **English in code** — identifiers, file and folder names, persisted field and storage key names, comments, commit messages, specs, plans and ADRs are English; texts the user sees stay in the app's UI language (German in Korbjäger and Pacetrainer). A domain term from `CONTEXT.md` takes its `_Code_` name (Kind is `Child`, Spiel `Game`, Kader `Roster`), never an ad-hoc translation. Fields of an outside API keep its spelling (the DBB's `ligaData`, `spielplan`) and get English names at the adapter. Korbjäger's existing German identifiers and Firestore fields are renamed by their own issues ([#2966](https://github.com/WolfSoko/wol-sok-mono/issues/2966) the fields, then [#2967](https://github.com/WolfSoko/wol-sok-mono/issues/2967) the identifiers), not piecemeal: persisted names need a migration. Until then the Korbjäger section below names them as the code spells them. Pacetrainer's few German identifiers (`Zusammenfassung`, `PlannedIntervall`) may be renamed by a change touching them, unless persisted. Every non-persisted name a change introduces or rewrites is English

## Linting & Formatting

- One workspace-wide `.oxlintrc.json`; there are no per-project lint configs. Add project-specific rules through `overrides` with a `files` glob.
- Type-aware linting is on (`options.typeAware`, backed by `oxlint-tsgolint`). It reads each project's `tsconfig.json` with TypeScript 7 semantics: no `baseUrl`, `paths` relative to `tsconfig.base.json` (`./libs/...`), and no `moduleResolution: node`/`node10`. Keep new tsconfigs on that layout or lint reports `tsconfig-error`.
- `@nx/enforce-module-boundaries` runs inside oxlint through the `@nx/oxlint/boundaries-plugin` bridge; tag constraints live in `.oxlintrc.json`.
- Boundaries are never disabled inline: `wolsok/no-boundary-disable` (`tools/oxlint/workspace-rules.mjs`, the workspace's own JS plugin, a leaf project `oxlint-workspace-rules`: `@nx/oxlint` gives every project an implicit edge on a local plugin's project, so it must import nothing from the workspace) fails on `eslint-disable`/`oxlint-disable` comments for the rule. Move the import behind a lib's path alias, or record the exception as an override in `.oxlintrc.json` (as for `apps/*/federation.config.js` and `libs/utils/version`).
- The workspace version (`version.json`) is read only through `@wolsok/utils-version` (`libs/utils/version`, `WORKSPACE_VERSION`, `releaseName(project)`), which declares the file as an input, so every task depending on it reruns on a release. `wolsok/no-version-json-read` (in the same `tools/oxlint/workspace-rules.mjs`) fails any other import or `read…()` of the file within one expression (`readFileSync(join(root, 'version.json'))`), but traces no path built in an earlier statement; `libs/utils/version` is exempt by an override in `.oxlintrc.json`. The plugin's spec runs the rules through oxlint itself: `npx nx test oxlint-workspace-rules`.
- Production sources never import test-only code: `wolsok/no-testing-import` (same plugin, on for `apps/*/src/**` and `libs/**/src/**` by an override in `.oxlintrc.json`) fails an import, `export … from`, `import()`, `import('…').Type`, `import x = require('…')` or `require()` of a `@wolsok/<lib>/testing` entry or a relative `testing` path, since those fakes call `jest.fn`/`vi.fn` at module load and the boundary rule counts `<lib>/testing` as `<lib>`. Test files there are recognised by their path inside the workspace (`TEST_FILES`: `*.spec.*`, `*.test.*`, `*.emulator.*`, `*.cy.*`, `*.mock.*`, `test-setup.*`, a `testing.ts` entry, anything below `testing/`); `tools/` and `e2e/` are not linted by it.
- The scripts under `tools/` are the project `tools` (tag `tools`, never depending on an app), with an inferred `lint` and `typecheck-tools` (`tsc` of `tools/tsconfig.tools.json`, `.ts` only). A module an app imports gets a nested project of its own (`tools/federation` is `tools-federation`, `tools/vite` is `tools-vite`): Nx records the app's import as a dependency, so inside `tools` every script's change would release the apps. Scripts import libs only through their path aliases, never a relative path into a lib's `src/` (the balance lab takes the engine's `/balance` entry, the fixture scripts the basketball data lib's `/testing`), and run as `tsx --tsconfig tools/tsconfig.tools.json`, since tsx reads only a root `tsconfig.json`, which the workspace lacks; `tools/tsconfig.json` only extends `tsconfig.tools.json`, so type-aware oxlint, which takes a file's nearest `tsconfig.json`, resolves those aliases too.
- oxlint only lints JS/TS. Angular templates are covered by a second, template-only ESLint setup: the root `eslint.config.mjs` (angular-eslint template rules for `.html` and inline templates, plus the per-project component/directive selector prefixes) is inferred as the `lint-templates` target by `@nx/eslint/plugin`. New Angular projects get their selector prefix added to `selectorPrefixes` in that file. The JSON-based `@nx/dependency-checks` rule is gone; keep package.json deps correct by hand.
- `nx format:write` / `nx format:check` run oxfmt (HTML, SCSS, Markdown and YAML are formatted through its Prettier-backed path).
- The SpeedDev cockpit (skill, roles, hooks) reaches sessions as the `speeddev` plugin on the claude.ai account, not as repo files; don't add `.claude/skills/cockpit/` or `.claude/hooks/cockpit/` back.

## Dependency Constraints

```
apps        → features, shared, utils, ui-kit
features    → shared, utils, ui-kit
shared      → utils
```

## Target Policy

- Root `.browserslistrc` and `tsconfig.base.json` govern everything — apps/libs inherit.
- **Do not bump targets in `libs/public/*`** — published packages, held back for consumer compat.
- **`apps/*-cdk` use `target: "ESNext"`** intentionally (Node runtime) — exclude from browser-target changes. Their `tsconfig.json` extends the root `tsconfig.cdk.json`, which holds that target; a new CDK app extends it too, never `tsconfig.base.json` directly.

## Native Federation

- `angular-examples` is the shell, remotes are `fourier-analysis-remote`, `bacteria-game-remote`, `shader-examples-remote`.
- Shared setup lives in `tools/federation/workspace-federation.js`; each app's `federation.config.js` only adds its name and `exposes`. A package skipped in one app must be skipped in all of them, or the shell and a remote disagree about the import map. The game lib's secondary entries (`admin-kit`, `watch`, and `testing`, the fake Firebase SDK the admin's specs take) and its engine (`@wolsok/feat-shared-bacteria-engine`, with `/testing` and the balance lab's `/balance`) are skipped there with the lib.
- `exposes` paths resolve from the workspace root (`./apps/<app>/src/...`), not the project root.
- **Nothing but the exposed module belongs in `src/app/remote-entry/`.** Native Federation maps the whole _directory_ of an exposed file to the remote's public name, so a sibling file imported with a static `import` from outside that folder is rewritten to `<remote>/Routes` and its exports vanish at runtime. That is why each remote's bootstrap component sits in `src/app/`, not next to `entry.routes.ts`.
- A remote also has to run standalone (its own e2e serves it that way), so check both: loaded through the shell _and_ opened on its own port.
- Remotes are listed in `apps/angular-examples/src/assets/federation.manifest.json` (dev) and `federation.manifest.prod.json` (prod).
- Each app has an `esbuild` target (`@angular/build:application`) wrapped by a `build`/`serve` target from `@angular-architects/native-federation`. Change build options on `esbuild`.
- `bacteria-game-remote` runs on Firebase Hosting (`firebase.bacteria-game-remote.json`, site `bacteria-wars`, domain `bacteria-wars.wolsok.de`), deployed by its `deploy` target together with the Firestore and Realtime Database rules. The shell's prod manifest loads the remote from there, and the shell reloads once when a navigation fails on a remote bundle a release replaced (`core/reload-on-stale-bundle.ts`). The old domain `bacteria-game.wolsok.de` is gone; `bacteria-game-remote-cdk` (stack `BacteriaGame`) only holds the new domain's CNAME, whose construct id must stay as it is.
- The game's legal pages live in `bacteria-game-remote`, not the lib: `/privacy` and `/impressum` (`src/app/privacy`, `src/app/impressum`, sharing `src/app/legal/`). Both name the provider from `SITE_OWNER` (`@wolsok/shared-legal`, `libs/shared/legal`: name, email, postal address, VAT ID), shown by its `SiteOwnerComponent` (`<wolsok-site-owner>`), as on RollaPolla's and wolsok.de's `/privacy` and `/impressum`, which also fills `siteOwner` in the support options for the footer's copyright line. The game lib's `support/` folder links to the pages from the footer under the main menu (the route paths are the lib's `legal-links.ts`, used by `app.routes.ts`) and offers the Android app or the PWA in a banner (`InstallOffer`), both only where `provideGameSupport` is set up: on the game's own site, never in the shell.
- The owner's admin area (ADR 0012) is the lib `feat-lazy-bacteria-wars-admin` (tag `feature:admin`, prefix `feat-lazy-bac-admin`), loaded by `/admin` in `bacteria-game-remote`'s `app.routes.ts` only, never through the exposed routes. It takes from the game only `@wolsok/feat-lazy-bac-game/admin-kit` (and, in its specs only, `@wolsok/feat-lazy-bac-game/testing`), has texts of its own in English and German, and must stay out of what every visitor loads: the remote's production `build` ends with `tools/bacteria-game/check-lazy-admin.mjs`, which fails when the admin's sources reach `main`, the polyfills or `Routes`.
- Exception: `bacteria-game-remote` is also a standalone PWA. Its federation build is `build-federation`; `build` then reruns `ngsw-config`, since the federation builder writes its files after Angular has hashed the output into `ngsw.json`.
- Error reports go to Sentry (org `wolsok`): the shell to `angular-examples` (`bootstrap.ts`, `core/core.module.ts`), the game to `bacteria-wars`, started only by the remote's standalone `bootstrap.ts` and `app.config.ts` (`src/app/error-reports/`), never by the lib or the exposed routes, and only where the environment has a `sentry` block (`environment.prod.ts`). The SDK is imported dynamically (`import()` in `error-reports.ts`), so it stays off the start's path; errors from before it loaded wait for it. Import it nowhere else but as a type. Errors only and no personal data (owner's decision of 2026-10-26): no tracing, Replay or sessions, `dataCollection.userInfo: false`, and `scrub.ts` drops the user, strips query, hash (`#friend=…`) and id-like tokens, and the attributes of click breadcrumbs (avatars name players in `aria-label` and `alt`). `@sentry/angular` is skipped in `workspace-federation.js`, so each app bundles its own copy. The release is `bacteria-wars@v<version.json>` (`releaseName('bacteria-wars')` from `@wolsok/utils-version`), created by `.github/actions/create-release`; a change to what is sent goes into the privacy policy (section 10) too.
- Fonts and icons are self-hosted: each app's global `styles.scss` imports the Fontsource faces (latin subsets) and `material-icons/iconfont/filled.css`, and nothing loads from Google Fonts (Angular's font inlining fetched them at build time, which failed the release build, and Google would get every visitor's IP). The shell imports the game's faces too (Atkinson Hyperlegible, Bricolage Grotesque, Cookie), since only the remote's JavaScript reaches it. The game's PWA caches them as `/media/**`.
- `nx serve angular-examples` only serves the shell. Use `nx run angular-examples:serve-all` to boot the shell plus all remotes (ports 4200-4203).

## Cloud Functions (Bacteria Wars)

- `apps/bacteria-wars-functions` is the game's server code (ADR 0011, 0012): 2nd-gen functions, codebase `bacteria` in `firebase.bacteria-game-remote.json`, region `REGION` in `src/config.ts` (the Firestore location of `bacteria-wars`). It takes the engine from `@wolsok/feat-shared-bacteria-engine` (`libs/features/bacteria-engine`, tag `feat-shared`, Node-only: no Angular, NgRx, RxJS, Firebase or DOM) and bundles it (`@nx/esbuild`, ESM, `thirdParty: false`); `firebase-admin` and `firebase-functions` stay external, at the versions in the app's own `package.json`, which a spec keeps equal to the workspace's.
- The documents the functions write and the game and the admin read are described once, in the engine's `state/cloud-records/`: the ban (`parseBan(data, toMillis)`, `banHolds`, end exclusive as the rules' `notBanned()`, and the Realtime Database mirror `mirroredBan`/`parseMirroredBan`), notice types, replay kinds and states, hide reasons, the admin statistics' figures and whether a stored replay plays back (`storedPlaybackRefusal` on `StoredPlayback`, which every writer stores through `storedPlaybackOf` and which "My matches" and the gallery's `fitsGallery` ask instead of a check of their own). Each side passes its own Timestamp mapping (`timestampMillis` in the functions' `src/timestamps.ts`, `millisOf` in the game and the admin); the admin takes them through `admin-kit`. A new shape both sides read goes there too.
- The client never calls a function: it writes command documents (`replaySubmissions`, `replayCommands`) that triggers process. Triggers run with retries off and are idempotent (`create()` or a transaction checks first).
- A command document's envelope (`uid`, `createdAt`, `expireAt` a day ahead: `COMMAND_ENVELOPE_KEYS`, `COMMAND_TTL_MS`), the replay command types, `parseReplayCommand` and the result (`CommandResult`, `{ ok, error?, at }`, `parseCommandResult`) live in the engine's `state/command-documents.ts`; the game and the admin write the envelope with `commandEnvelope` (game lib `storage/command-envelope.ts`, in the admin kit). In the functions, `runCommandDocument` (`src/commands/run-command-document.ts`) checks that the writer is the command's `uid`, turns a throw into `internal` and writes `result` back; `runAdminCommand` and `runReplayCommand` keep only what their commands do, and a new command collection runs through it too.
- The boards (`src/boards/`) are written by functions only: entries carry no uid (`boardMembers/{uid}.entryIds` maps them), `rebuildTop` alone writes a board's top document, and every composite query has its index checked by `indexes.spec.ts` against `firestore.indexes.json`, since the emulator enforces none.
- `test` runs the pure specs; `test-emulator` runs `*.emulator.ts` against the Firestore emulator on ports of its own (`emulator.json`). Each emulator spec takes its `db` from `useEmulatorDb()` (`src/testing/emulator.ts`, which starts the app once and clears the ban cache and Firestore before each test, on the project `test-emulator` names) and its Realtime Database from the one fake, `fakeRealtime()` (`src/testing/fake-realtime.ts`: a tree like the real one, with a log of what was written in `calls`, a hook-free `peek`, `failRemoving` and race hooks); `src/testing/` is test code, kept out of `tsconfig.app.json`. The game's rules are tested the same way in `apps/bacteria-game-remote/rules-test` (`bacteria-game-remote:test-emulator`). CI runs both targets.
- Errors go to the Sentry project `bacteria-wars-functions` (`src/error-reports.ts`, DSN `SENTRY_DSN` in `src/config.ts`): `main.ts` calls `initErrorReports()`, which starts `@sentry/node` only in a deployed function (`K_SERVICE` set, not the emulator or Jest), and wraps every exported handler in `withSentry(handler)`, which captures, waits for `flush` and rethrows, so retries stay as they were. A new function gets the wrapper too; handler modules stay free of Sentry. `@sentry/node` is external and in the app's `package.json` at the workspace's version (`package-json.spec.ts`).
- Handler modules import `firebase-functions/logger`, not `firebase-functions`: the root export loads the admin auth stack, which Jest on Node 22 cannot require.
- Re-running a replay (`boards/verify.ts`, judged by the engine's `replayVerdict`: `verified`, `unverified`, `balance-mismatch` or `unplayable`, the last stored as `unverified`) costs real CPU: `gpu-int`, the only ruleset ranked attempts take, plays at about 7 ms a tick on `intSimulation`, so a 10-minute match takes minutes. Specs never replay whole matches: `verifyDailySlice` takes the verifier as a parameter, and `verify.spec.ts` mocks `replayVerdict`. `playReplay`, the balance lab, the replay viewer (`ReplayScene`) and the CPU bench play a match through the engine's `MatchRun` (`state/match-run.ts`: arena, last tick, frame deadline, seek, result with checksum); a new loop that plays a match on without a player uses it too, never its own `engine.tick` loop. The live match still ticks in `GameStateService.advance`. Firestore holds no arrays in arrays; flatten what a function stores.
- `hourly` (`boards/hourly.ts`) is exported only with `HOURLY_ON` in `src/config.ts`; set it to `false` to take it out of a deploy.
- `featureBest` (`gallery/feature-best.ts`, the gallery's daily pick into `publicReplays`) is exported only with `FEATURE_BEST_ON` in `src/config.ts`, on since the gallery's pages and the Replays view of `/admin` shipped (ADR 0011 rollout step 6); set it to `false` to take it out of a deploy.
- Account deletion erases the player's data (ADR 0012, owner's decisions of 2026-10-26). Where that data lives is one table, `PLAYER_DATA` (`src/erasure/player-data.ts`): every collection, document and Realtime Database node with the part that erases it and how (`doc`, `tree`, `field`, `node` by path or field; `custom` by the part's own code; `keep` with its reason), and `player-data.spec.ts` fails on a `match` path of `firestore.rules` or a node of `database.rules.json` without an entry, on a path listed twice or below a `tree`. A new collection or node of a player gets its entry there, and its erasing too. `erasePart(part, ctx, uid)` (`src/erasure/erase.ts`) is the one entry point of the three `auth.user().onDelete` triggers: `account` for `deletePlayerBoards` (`admin/accounts.ts`: boards, pairs, bans, audit and the owner's commands about the player, count), `social` for `deletePlayerData` (`social/delete-player.ts`: `players/{uid}/**`, profile, the player in other players' lists, queue, open rooms, invites, presence and both mirrors) and `replays` for `deletePlayerReplays`, which no longer deletes replays: `replays/forget.ts` takes the uid out of `players`, seats, `optOut` and `reports`, and the replay stays for the statistics until its `expireAt` (none while still public). Each part deletes its plain entries through `eraseListed` where its order needs it (`replays` first, its pending `replaySubmissions` and `replayCommands`; `account` and `social` after their reads); `acceptReplay` reads its submission in its slot and store transactions and drops one that is gone (`withdrawn`), so taking the slot marks the submission (`slotTaken`) rather than deleting it. `erasePlayer` runs every part; `erasure/erasure.emulator.ts` tests the erasure, table-driven for the plain entries.
- `guestCleanup` (`admin/guests.ts`, daily at 03:41 UTC) deletes guest accounts (no provider) unused for `GUEST_IDLE_DAYS` (90); exported only with `GUEST_CLEANUP_ON`, on together with the friends-only status rule, which ships only after "Mirror friend lists" (`presence.backfill`) has run once in production. Auth's bulk `deleteUsers` fires no `onDelete`, so it runs `erasePlayer` (`erasure/erase.ts`) for each guest first and deletes the account only once that succeeded. It lowers `stats/accounts` once a batch by the decrements its erases claimed (`accountCounted` cleared in a transaction, so each account counts down once), never once a guest.
- The friend lists are mirrored into the Realtime Database by `mirrorFriend` and `mirrorRequest` (`social/mirror.ts`): `statusReaders/{owner}/{reader}` (for the coming friends-only read rule of `status/{owner}`) and `listedBy/{uid}/{owner}/{friends|requests}` (where the deletion finds the player in others' lists). Functions only: the database rules close both to clients. Both triggers retry; each re-reads the entry after its write and writes again if it changed, so out-of-order events end right. Ids the Realtime Database takes as no key (`isRealtimeKey` in `admin/realtime.ts`) are skipped everywhere, and the Firestore rules take only uid-shaped ids in `friends`, `requests` and `challenges`. The admin command `presence.backfill` adds what is missing and removes entries without a list entry.
- The player's replay command `forget` ("Delete" in "My matches", `replays/forget.ts`) takes them out of the replay and its public copies; allowed while banned, like every deletion, and refused (`ranking`) while the boards may still rank the match, an online match still `waiting` for its second report included (`stillRanking` in `replays/forget-plan.ts`).
- Its `deploy` target (`firebase deploy --config=firebase.bacteria-game-remote.json --only functions:bacteria --force`) calls the Firebase CLI itself, not `nx run bacteria-game-remote:firebase`: the game's hosting deploy runs that task in the same release, and the second, nested run of it failed every functions deploy. It runs in the `non-cdk` leg of `deploy.yml` whenever a release affects the app, which includes every change to the game's engine (`feat-shared-bacteria-engine`), since the app imports it. `--force` deletes functions of the `bacteria` codebase that are gone from `main.ts`, so taking a function out of the exports takes it out of production. The game's hosting deploy leaves the functions alone (`--only hosting,firestore,database`). It runs `firebase deploy` through `deploy/retry-once.ts` (`tsx`), which reruns a failed deploy once after 30 s, so a single transient error of Google's API no longer fails the release; the healed failure stays visible as a `::warning::`, a second failure fails the deploy. The retry decision is `runWithOneRetry` (`deploy/run-with-one-retry.ts`), spec'd in the app's `test` target.
- Every Firebase `predeploy` that runs `npm install` for a function (`firebase.bacteria-game-remote.json`, `firebase.pacetrainer.json`, `firebase.rollapolla-analog.json`) passes `--legacy-peer-deps=false`: deploys run inside `npx nx`, which exports the root `.npmrc` as `npm_config_legacy_peer_deps=true`, and the lock written that way lacks required peers, so Cloud Build's `npm ci` refuses it (`Missing: … from lock file`). A spec in each app keeps the flag (`package-json.spec.ts`, `firebase-deploy.spec.ts`); a new function config gets both.

## Android App

- `apps/bacteria-wars-android` is a Gradle project, not a web build: a Trusted Web Activity that opens `https://bacteria-wars.wolsok.de` (the `bacteria-game-remote` PWA) fullscreen in Chrome. Game changes go into the PWA; the app picks them up with the next web deploy.

## Testing

- **Unit (Jest)**: colocated as `<file>.spec.ts`; mock external services; keep fast and deterministic
- **Spec typecheck**: Jest transpiles without type checking, so fakes and calls in specs drift from the real types unnoticed. A project whose specs must typecheck gets an empty `"typecheck-specs": {}` target (command `tsc -p {projectRoot}/tsconfig.spec.json --noEmit`, inputs and caching from `targetDefaults` in `nx.json`), which CI runs among the affected targets; `feat-lazy-bacteria-game` has one. Not the same as the `typecheck` target `@nx/vite` infers for some projects, which checks the lib or app sources, not the specs
- **Unit (Vitest)**: used in Vite-based projects (check `project.json` for the `@nx/vitest` plugin / `@nx/vitest:test` executor)
- **E2E (Playwright)**: in `apps/<app>/e2e/`; page objects in `e2e/pos/`, fixtures in `e2e/fixtures/`
  - Start every `webServer` through an Nx target (`npx nx serve <app>`, `npx nx run <app>:<target>` for a `continuous` target) with `reuseExistingServer: true`. Inside an Nx task, Nx starts those targets, not Playwright: Nx stops and restarts continuous tasks between the batches an Nx Cloud agent runs, so a spec can find its servers still booting after the `--wait-for-webserver` gate already ran elsewhere, and a second start from Playwright fails on the taken ports ("Process from config.webServer exited early"). So every such entry comes from `nxServer(target, url, { cwd, timeout })` (`@wolsok/shared-e2e-server`, `libs/shared/e2e-server`), whose command only waits for the URL (`src/wait-for-server.mjs`) where `NX_TASK_TARGET_PROJECT` is set; the plugin still infers the dependency from the `nx run` command, read outside a task. Only then does `@nx/playwright` make the atomized `e2e-ci--*` tasks depend on those servers and wait for them, so several spec files on one Nx Cloud worker share them. A server Playwright starts itself clashes with the next spec file on the same worker (see `rollapolla-analog`). A static server (`@nx/web:file-server`) serves `staticFilePath` and `dependsOn: ["build"]` with `watch: false`, not a `buildTarget`: with `buildTarget` it runs a nested `nx build`, which Nx refuses as a recursive task invocation inside a shared run. Exception for now: `angular-examples` (the federation shell, one spec file) still lets Playwright start its server in CI; with the inferred serve dependency its page did not render on the Nx Cloud workers, while it passed locally.
- **Emulators on the Nx Cloud workers**: the workers download the Firebase emulators (`npx firebase setup:emulators:<name>`) in an init step of `.nx/workflows/workers.yml`, after `npm install` and before any task: the CLI otherwise downloads one on first use with a non-atomic copy, and a second emulator task on the same worker started Java on the partial jar and failed within seconds (#2960). A Firebase config using a new downloadable emulator (`pubsub`, `storage`, `dataconnect`; the UI unless `ui.enabled` is `false`) gets its step there; `tools/ci/nx-cloud-workers.test.mjs` (`npx nx test tools`) fails without it, and when `stop-after` in `.nx/ci-config.yaml` differs from the targets of `ci-cd.yml`'s `nx affected -t` call
- **GPU cross-check (Playwright, no server)**: `libs/features/lazy/bacteria-game/playwright.config.ts` runs the deterministic simulation's integer shaders on SwiftShader against the TypeScript reference, tick by tick (`gpu-crosscheck/`, ADR 0015). It is inferred as the lib's `e2e-ci--*` target, so `nx affected` runs it in CI. The goldens in `golden-gpu-int.json` are regenerated whenever the scenarios, the reference or the hash change; a change to what the passes compute also needs a `BALANCE_VERSION` bump, a scenario change does not; `golden.spec.ts` (Jest) recomputes them from the reference. The same check plays whole matches through the game's `gpuSimulation` (`SIM_SCENARIOS`) against `golden-gpu-sim.json`, which `sim-golden.spec.ts` keeps equal to `intSimulation`, and runs the on-device self-test; its own hashes are `SELF_TEST_GOLDEN` (the engine's `state/gpu-int/self-test-golden.ts`, with `GPU_SELF_TEST_VERSION` bumped on every change), kept in step by `self-test-golden.spec.ts`. `golden-replay.spec.ts` (in the engine lib, `libs/features/bacteria-engine/src/lib/state/`) keeps a result of `golden-replay.json` per `BALANCE_VERSION` for each ruleset: `cpu` on `BacteriaSimulation`, `gpu-int` on `intSimulation`
- **Plugin E2E (Jest)**: `apps/nx-aws-cdk-v2-e2e` exercises `@wolsok/nx-aws-cdk-v2` in a generated throwaway workspace. ## Performance Gates

Planned and phased in [ADR 0014](docs/adr/0014-performance-gates-in-ci.md); this section says what is in place. Keep it current with each phase.

- **In place, blocking** (phase 1): Angular budgets on the `production` configuration of each Angular app's `esbuild` target (`portfolio`: `build`), measured through the federation build as CI runs it.   - `anyComponentStyle` as before (warning 6 kB, error 8 kB in the game's apps), with no warning left: a stylesheet near the limit gives a part of its component a component of its own (the HUD bar `hud-bar.component.ts`, the training's `menu/mission-list.component.ts`) or groups rules it repeats, rather than raising the limit.
  - pacetrainer and rollapolla-analog build with Vite (Analog) and have no Angular budgets.
- **In place, report-only** (phase 2, since 2026-10-27, blocking after two weeks): the `perf` target on `feat-shared-bacteria-engine` runs `tools/perf/engine-bench.mjs`, which bundles the engine's `src/index.ts` with esbuild and plays fixed replays (the golden replay on `cpu` and `gpu-int`, and `tools/perf/fixtures/expanse-heavy.json`), comparing each one's median time as a ratio to a calibration loop against `tools/perf/engine-baseline.json`: warns above +10%, fails above +20%, asks for a lower baseline below −10%, and fails when a replay plays differently (checksum, ticks, outcome), no longer parses, or the baseline was measured on another Node major than `.nvmrc`'s (V8 optimises differently, so its ratios don't compare). It is cached, runs alone on its worker (`parallelism: false`), takes about 1.5 minutes and writes its table into the job summary. `--report-only` keeps it from failing until the two weeks are over; the baseline holds the CI workers' ratios on Node 24 (they don't carry over between machines, and not even between all CI workers: one run measured 40-50% above the others, so the report names the CPU, and the two weeks decide whether baselines go per CPU model), so a new baseline (a `perf(feat-shared-bacteria-engine): ...` commit of its own, also due when `BALANCE_VERSION` changes the checksums) takes its ratios from the `perf` output of a CI run; `--update` writes the local machine's, useful only for the checksums.
- **In place, report-only** (phase 3, since 2026-10-27): `apps/bacteria-game-remote/e2e/perf.spec.ts` (Chromium only) plays up to 20 s (at least 8) of a campaign match against the computer on the CPU simulation (`?sim=cpu`), with `Math.random` pinned to a seed by an init script, and reports the frame interval (p50, p95, max), long tasks and the engine's time per tick, each also as a ratio to the calibration loop run in the page. The table goes to the log (and the job summary where `GITHUB_STEP_SUMMARY` is set), the numbers into the attachment `frame-time.json`; it fails only when nothing was measured. On SwiftShader the frames take about 67 ms and a tick about 2.5 ms: the painting, not the engine, sets the pace there.
- **In place, report-only** (phase 4, since 2026-10-27): Lighthouse CI (`@lhci/cli`) as a `lighthouse` target on `portfolio` (every prerendered route, listed in its `lighthouse.json`, which `app.component.spec.ts` keeps equal to `app.routes.ts`), `angular-examples` (`/`) and `rollapolla-analog` (`/`, `/polls`), each after its `build`, cached, alone on its worker. `tools/perf/lighthouse-run.mjs <app>` runs `lhci autorun` on Playwright's Chrome (`CHROME_PATH` wins where set), with the app's `apps/<app>/lighthouse.json` (what to serve, which pages) and the shared settings it holds itself: 3 runs per page, mobile defaults, warnings only (LCP 2.5 s, TBT 200 ms, CLS 0.1, 1.6 MB), uploaded to temporary public storage in CI (links in the log), `.lighthouseci/` elsewhere. rollapolla's build is Nitro's `firebase` preset, which listens nowhere: `tools/perf/serve-firebase-function.mjs` serves its public folder and hands every other path to the exported function, as Hosting does; its SSR reads the real project's public polls. The public replay pages of the game (a Cloud Function behind Hosting) are not measured yet.
- **Rules**:
  - A failing gate is fixed in the code, not by raising the limit. Raise a budget or baseline only for growth you want, in its own `perf(<project>): ...` commit, with what grew, by how much and why in the PR body. Lower it when a gate reports a gain.
  - Don't compare absolute milliseconds from CI: the Nx Cloud workers are shared and vary. Runtime gates compare against a calibration loop run in the same process.
  - CI has no GPU. A change to the GPU simulation or the GL painters needs a manual check on a real device, noted in the PR.
  - New engine code must stay cheap per tick: online matches, replays, ranked matches and the Cloud Functions' verification all run the CPU simulation.

## Commits & PRs

- **Conventional Commits** enforced by commitlint: `feat(scope): ...`, `fix(scope): ...`, `chore(scope): ...`
- **Valid scopes** = any Nx project name (`npx nx show projects`) + `release`, `nx`, `github`, `dev-deps`, `deps`, `tools`. No free-form scopes (e.g. `mf`, `ui` will be rejected).
- Pre-commit: Husky + lint-staged (runs automatically)
- **Before every commit**:
  1. `npx nx format:write`
  2. `npx nx affected -t lint,lint-templates`
- PR scope: include summary, UI screenshots if visual, linked issue; cleanups of the touched code belong in the PR (see Engineering Principles), larger unrelated refactors get their own PR
- **Always request a CodeRabbit review** after opening a PR: this repo gets no automatic reviews
  (fewer than 10 stars), so comment `@coderabbitai review` on the PR and work through the findings
- **When CodeRabbit and Codex are both rate-limited**, don't wait for them: review the change
  yourself (`/code-review`) and run `/simplify` on it, then fix what they find
- **Merge it yourself once it is done**: `/code-review` and `/simplify` findings applied, every
  review thread answered or resolved, and CI green on the current head. Squash-merge (the
  history on `main` is one commit per PR). A human approval is not part of "done" here

## General Guidelines for working with Nx

- For navigating/exploring the workspace, invoke the `nx-workspace` skill first - it has patterns for querying projects, targets, and dependencies
- When running tasks (for example build, lint, test, e2e, etc.), always prefer running the task through `nx` (i.e. `nx run`, `nx run-many`, `nx affected`) instead of using the underlying tooling directly
- Prefix nx commands with the workspace's package manager (e.g., `pnpm nx build`, `npm exec nx test`) - avoids using globally installed CLI
- You have access to the Nx MCP server and its tools, use them to help the user
- For Nx plugin best practices, check `node_modules/@nx/<plugin>/PLUGIN.md`. Not all plugins have this file - proceed without it if unavailable.
- NEVER guess CLI flags - always check nx_docs or `--help` first when unsure
